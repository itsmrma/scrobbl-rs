    Prototype notes and evidence still needed

    The English interface above is a proposal. The session, callback, persistence, restart and refresh results shown here are a model, not technical proof. The desktop helper is only a packaging alternative over SSH; it has not been built.

    • The existing backend accepts only one exact loopback Host/Origin. Its normal LAN/VPN and optional HTTPS support still need implementation. The proposed temporary flow must remain separate from the everyday interface.
    • Open the whole app through the tunnel, sign in there, then configure/connect Spotify. Do not copy the LAN session cookie or move a callback URL between hosts. Use the same browser and profile throughout.
    • The proposed server-side attempt belongs to that local authenticated session; state is one-use and expires after ten minutes. Explicit cancellation and cancellation on restart in this model are proposed recovery behavior, not a claim about existing code.
    • For the current backend the local port must match SCROBBL_PORT. A different local port requires an explicitly configured allowed origin and matching redirect URI; an automatic fallback would break the current contract.
    • SSH encrypts the PC-to-SSH-host segment after server identity verification. The target shown is loopback on that same host; Docker must expose an appropriate endpoint there. Forwarding from that host to another machine over HTTP would add an unencrypted segment.
    • The browser sends the authorization code and session through loopback + SSH; the server exchanges the code directly with Spotify over HTTPS and stores tokens in its persistent database. The user may enter app credentials in the browser via the tunnel. No token or database copying is part of the journey. Everyday LAN HTTP still carries session and archive traffic without TLS, as already accepted for the private installation.
    • Before release: verify SSH availability and forwarding permissions on Windows/macOS and TrueNAS/Portainer, host key verification, container reachability, local port conflict, exact redirect registration, real Firefox callback/session/state behavior, cancellation/expiry/replay/wrong-session rejection, failed exchange, persistent token storage, refresh and collection with browser/tunnel closed and after server recreation. Verify HTTPS cookies/proxy/Origin and Safari consultation separately.
    • Reconnection after an invalid or expired refresh token repeats authorization. A transient refresh/network error should retry on the server rather than automatically require authorization.

    Sources: Spotify redirect URIs, Spotify refresh tokens, OpenSSH forwarding. Rechecked 20 October 2026. Spotify currently documents six-month refresh-token lifetime for Developer Dashboard apps; ordinary refresh does not extend it.
